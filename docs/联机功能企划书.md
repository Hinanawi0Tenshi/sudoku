# 数独工作台 · 联机功能企划书

> 状态：方案稿（未实现）
> 目标项目：`sudoku-studio`（已上线，纯静态托管，含数独 / 杀手数独 / 扫雷三款游戏）
> 用户选定方向：**房间 + 观战/聊天**、**实时同屏对战**
> 平台约束：优先使用 WorkBuddy 原生能力（静态托管 + cloud-service），不引入第三方后端

---

## 0. 摘要

在现有三款单机游戏上叠加轻量联机。本期不做账号体系强绑定，以「房间码」为主入口，
聊天与观战走准实时（秒级轮询），同屏对战提供「轮询版 MVP」与「WebSocket 真实时版」两套预案，
按体验反馈再决定是否升级。

核心依赖：**WorkBuddy 静态托管（现状）+ cloud-service 的 Database / Auth / Storage 模块**。
密钥不进代码，鉴权由平台 Origin 精确匹配完成。

## 1. WorkBuddy 能提供的服务（能力清单）

| 服务 | 形态 | 对联机的用途 |
|---|---|---|
| **静态托管（sites）** | 现状，纯前端分发 | 前端页面、游戏逻辑、OCR vendor 分发，**保持不变** |
| **cloud-service · Database** | REST `/.cloud/database/rest/**` | 房间、成员、对局、聊天消息、排行榜的结构化存储与查询 |
| **cloud-service · Auth** | REST `/.cloud/auth/v1/**` | 可选：用户登录、身份隔离（多端同账号、防冒名） |
| **cloud-service · Storage** | REST `/.cloud/storage/**` | 可选：头像、对局截图、分享图 |
| **cloud-service · LLM** | REST `/.cloud/llm/chat/completions` | 可选：AI 陪练提示、赛后复盘文案 |
| **发布/部署** | `workbuddy_sites_deploy` | 覆盖式发布，链接不变 |

**关键边界（务必先对齐）**：cloud-service 全部模块均为 **REST 请求-响应模型，无 WebSocket / 流式推送**。
因此"实时"二字在本平台有两层含义：

- **准实时**：前端每 1~2 秒轮询一次 Database，体验上为秒级同步——**纯 cloud-service 即可**。
- **真实时**：毫秒级双向同步，需要长连接——**cloud-service 不支持**，须走动态 Node 服务（见 §5 路线 B）。

## 2. 功能拆解与对应服务

| 功能 | 数据载体 | 实现方式 | 是否需要 WebSocket |
|---|---|---|---|
| 创建/加入房间 | Database `rooms` 表 | REST 写入 + 轮询读取 | 否 |
| 房间内成员列表 | Database `room_members` 表 | REST | 否 |
| 文字聊天 | Database `messages` 表 | REST 写入，前端轮询拉取 | 否（准实时够用） |
| 观战 | Database `board_snapshots` 表 | 房主定时写盘面快照，观战者轮询 | 否 |
| 异步竞速（同题比时间） | Database `matches` 表 | REST 计分，结束比对 | 否 |
| **实时同屏对战** | 路线 A：高频轮询 `board_deltas` 表 / 路线 B：ws 通道 | A=秒级；B=毫秒 | **A 否 / B 是** |
| 排行榜 | Database `leaderboard` 表 | REST 读写 | 否 |

## 3. 数据模型（MVP 草案）

```
rooms
  id            // 房间码（短串，如 6 位）
  game          // sudoku | killer | mines
  host_uid      // 房主
  status        // waiting | playing | finished
  created_at
  config        // 难度、模式等 JSON

room_members
  room_id, uid, role(host|player|spectator), joined_at

messages
  room_id, uid, text, created_at

board_snapshots      // 观战用
  room_id, uid, snapshot(JSON 盘面), updated_at

board_deltas         // 同屏对战路线 A 用
  room_id, uid, delta(JSON 增量), seq, created_at

matches              // 竞速/对战结算
  room_id, uid, result, score, duration_ms, finished_at

leaderboard
  uid, game, best_time_ms, wins, updated_at
```

> 实际字段以接入时的 `code-generation.md` 为准；此处仅为对齐需求。

## 4. 推荐架构（MVP，纯 cloud-service）

```
┌──────────────┐         HTTPS (REST)        ┌─────────────────────┐
│  浏览器前端    │  ───────────────────────▶  │  WorkBuddy          │
│ (现有静态站点) │  ◀───────────────────────  │  cloud-service      │
│              │   轮询 / 写入               │  Database/Auth/...  │
│  + 联机 UI   │                            │  (托管,Origin 鉴权) │
└──────────────┘                            └─────────────────────┘
```

- 前端仍是静态托管，**不动现有游戏代码与部署形态**。
- 新增一个 `js/online/` 模块：封装 SDK 初始化（endpoint + publishableKey 来自 publicConfig）、
  房间 CRUD、轮询循环、聊天渲染。
- 鉴权：先做「游客 + 房间码」即可；若要账号体系再开 Auth（§1）。
- **密钥安全**：`publicConfig` 在前端是公开的（publishableKey 本就在浏览器），
  真正的后端密钥永不返回前端，服务器用 Origin 精确匹配——**不触碰项目目录公开上传的红线**。

## 5. 实时同屏对战的两条路线

### 路线 A：准实时（推荐先做，纯 cloud-service）

- 双方各持本地盘面，每次操作把增量写入 `board_deltas`（带 `seq` 序号）。
- 前端每 1 秒轮询一次，按 `seq` 拉取对方增量并应用。
- 体验：操作有约 1 秒延迟，对解数独/扫雷**基本可接受**；对"比谁手快"的竞速也够用。
- 优点：零部署改动、零运维、密钥安全、当天可上线。
- 缺点：非真实时，轮询频率受 REST 限流约束（需控制到 1~2 秒/次）。

### 路线 B：真实时（动态 Node 服务 + WebSocket）

- 部署形态从 `static` 改为动态单端口服务：Node(Express) 同时托管静态文件与 `ws` 长连接。
- 双方经 WebSocket 双向推送盘面增量，毫秒级同步。
- 代价：
  - **改部署形态**，现有根路径假设、`VENDOR` 相对路径、纯前端架构都要重新审视。
  - 后端源码随目录**公开上传**——任何外部密码不能写进项目目录（红线）。
  - 维护成本显著高于路线 A。
- 结论：**仅当路线 A 的秒级延迟被实测证明不可接受时，才上路线 B。**

## 7. 风险与注意

- **密钥不进代码**：前端只用 `publicConfig` 的公开字段，绝不手写任何长寿命密钥。
- **整目录公开上传**：本项目发布是整目录覆盖，`docs/` 下的设计文档会随下次发布公网可见。
  本企划书若不便公开，请把其移出项目目录（如 `D:/Downloads/` 上层）后再发布。
- **cloud-service 配额/计费**：开通会在 UI 弹确认框，需用户授权；占用账户应用额度。
- **REST 轮询限流**：高频轮询（尤其路线 A 同屏对战）需把频率压在 1~2 秒/次，避免触发限流。
- **数据隔离**：一个 cloud-service 环境对应一个应用，数据不跨应用；复用 `sudoku-studio` 的 id 即可保持 Origin 匹配。

## 8. 需要拍板的决策点

1. **同屏对战先做路线 A（轮询）还是直接上路线 B（WebSocket）？** —— 建议 A 起步，按体感再定。
2. **要不要账号体系（Auth）？** —— MVP 可先用「游客 + 房间码」，省去登录 friction。
3. **聊天/观战是否需要登录才能用？** —— 影响 Auth 是否随阶段 1 一起开。
4. **本企划书是否允许随项目公开？** —— 否的话请指定存放位置。
