## 不能破坏的技术约束
- `js/games/sudoku/07-ocr.js` 的 `VENDOR = 'js/vendor/'` 是相对路径 → 必须部署在根路径，挪子目录会 404。
- `js/vendor/` 必须自包含（worker + 4 个 core + eng.traineddata.gz），**零 CDN 外链**，别改成 CDN。
- `js/vendor/tesseract/` 的 4 个 core 都要留，Tesseract 按 SIMD 支持自己挑一个。
- 全是 `*.wasm.js`（内嵌 wasm），没有裸 `.wasm`，别换。
- 脚本用数字前缀保证加载顺序，普通 `<script>` 而非 ES modules（为了 file:// 可用）。
- 测试风格：纯 Node 内置模块，零 npm 依赖。

## 架构（2026-10-13 重构）
- 七款游戏全部实装：数独、杀手数独、扫雷、数字华容道、2048、华容道、数织。
  - **数织（js/games/nonogram/）**：八个文件。和其它品类**反过来**——先有画，线索从画里读出来。
    所以"画从哪来"是核心问题：随便生成一张网格当不了题（线索太弱会多解或推不动）。
    图库 41 张全部离线验过「解唯一」+「纯逻辑可不可解」，0 张多解，4 张需假设（归大师档）。
    几何图形用公式画（心/星/环/菱形/三角/十字/箭头/六边形/斜叉），物件手绘字符画。
  - **提示是必然结论，不是建议**：行求解器把该行线索的**所有**合法摆法枚举出来逐格统计，
    每种摆法都盖住的格子必然是实心。单测有一条性质测试逐格核对提示与真解，1721 步零冲突。
  - **`warpQuad` 的缩放方向曾经是反的**（已修，收益极大）。
    循环里拿 H 映射的是**输出坐标**，要的是 dst→quad；写成 `homography(quad, dst)`
    会得到逆向缩放——源 594、quad 594、输出 720 时，棋盘在输出里只占 488（缩小而非放大）。
    `extractCells` 里的 `refineGrid` 会重新找网格线，把错位掩盖了，所以逐格路径一直没暴露。
    **修完照片场景从 25% 直接跳到 97%**——之前我判断"照片是 JPEG+重采样糊掉了，要上 OpenCV"
    **是错的**，真凶就是这一行。
    教训：**先量清楚瓶颈在哪一环，再谈换算法**。
  - **OCR 数字识别改用"模板匹配"**（js/games/sudoku/07b-digit-match.js）。
    通用 OCR（Tesseract）是给"成行文字"设计的，数独是一堆孤立数字，它靠上下文反而吃亏，
    而且 wasm 包 17MB，占整个项目 42%。
    模板在运行时用 8 种字体 × 2 个字重 × 9 个数字现画（144 个），零资源零依赖。
    归一化必须**按高度缩放、水平居中、保持宽高比**——按包围盒拉满的话细长的"1"
    会被拉成和"8"一样宽，两者就分不开了。
    实测理想条件 72/72、缩小加噪 36/36，匹配分 0.78~1.00。
    接在逐格路径最前面，分够（≥0.62 且和第二名差 ≥0.06）就直接采信，否则退回 Tesseract。
  - **照片场景的瓶颈不是数字分类，是网格对齐残差**（未解决）。
    模板匹配很准（36/36），但照片场景仍只有 8/32——透视重采样 + JPEG 之后
    网格复检有残差，切出来的格子本身就是歪的。要救得从切格下手，不是从识别下手。
  - **OCR 区分"印刷题面"和"铅笔候选数"：靠墨色，不靠尺寸**（已解决）。
    尺寸判据天生不成立：候选数是 3x3 铺满整格的小字，**包围盒反而比线索字还大**。
    墨色是正交信号且和清晰度无关（模糊让整体一起变浅，相对深浅还在）：
    实测印刷体 22~41、铅笔 133~152，差 90 个灰阶。
    判定用"排序后相邻项的最大间隙"，**门槛必须定 60 以上**——
    定 30 时照片经 JPEG 压缩产生的假断层会误触发，正确数从 8 掉到 6。
    另外"排除笔记格"只能排除**墨色明确否决**的：尺寸单独否决的格子仍可能真线索，
    一刀切会把照片场景的正确数从 8 砍到 6。
    夹具在 tests/ocr-test.js 的 notes 场景（硬门禁）。
  - **弹窗编辑器要从"当前状态"起步并每次重绘**。OCR 修正弹窗原先 `new Array(81).fill(0)` +
    只填被点的那一格 → 看着像"识别结果全丢了"；`onclick` 只改数组不重绘（`_refresh` 定义了从没调用）
    → 点了没反应。两个 bug 都是"本地变量和显示脱钩"。
  - **拖拽刷新不能读渲染时缓存的值**：`view.touch(i)` 原先读 `c._v`（上次整块渲染缓存的），
    拖拽时缓存还是旧的，toggle 的是旧状态——黑块要等松手整块重画才出现，玩家看不到划到哪。
    值必须由调用方传进来。
  - **撤回的粒度是"一次操作"**（一划/一点），不是一格：拖过一片后按撤回，期望整片回来。
  - **线索灰化必须按真解逐格判，不能比"实心段长度"**。比长度有歧义：一行里 2 个格子
    位置放错了长度仍是 2，于是行线索变淡、列线索不变淡——两边都没算错，但玩家看到
    "左边完成了上面没有"，判定成游戏坏了。按真解判两个方向必然一致。
    注意行的下标是 `r*w+i`、列是 `i*w+c`，两套公式不一样（写错过一次）。
  - **图形必须裁到外接矩形**（`crop()`）：不裁的话四周留出整行整列空格，线索里冒出一堆 0，
    玩家以为线索丢了。实测 41 张里 23 张是这样。裁完长宽不再相等，这是正常的。
    注意 `crop()` 只裁**边缘**——内部空行空列裁不掉，只能改画法（杯子踩过：把手和杯身之间
    空了一整列）。改画法时还要重验唯一解（细把手会多解）。
  - 形状全靠「打印出来看」才发现的问题：三角条件写反成窄条、六边形成了圆角矩形、
    爱心凹口太浅像圆疙瘩、钥匙线索太弱有两个解。**公式生成的图形一定要肉眼验一遍。**
  - 核心和求解器的键/线索编码必须共用一套（华容道那边踩过，这里注意）。
  - **华容道（js/games/klotski/）**：六个文件。可达局面只有 2.6 万个，所以**开局把
    所有局面到出口的最短步数一次算完**（两遍 BFS，约 0.1 秒）——提示永远最优、难度是
    精确值、出题就是按距离筛一个局面。这是六款里唯一不需要"搜索/降级"的。
  - **两遍 BFS 而不是枚举目标族**：目标是「曹操在底部中间」的一整族（964 个）。
    枚举它们当源要 1.4 秒，比 BFS 本体（0.32 秒）贵四倍；改成先从经典开局 BFS 找出
    可达状态、再挑出其中的目标态当第二遍的源，两遍共 0.1 秒。
  - **局面键按形状编码，不按块身份**：四个卒互换、两个竖块互换对玩家是同一局面，
    不合并状态数会白翻好几倍。而且核心和求解器**必须用同一套编码**——各写一套的话
    查表永远查不到（这里踩过：经典开局返回 -1，排查了一轮）。
  - 经典「横刀立马」= 116 步（按走一格算一步）。
  - **空格必须一眼看得出是"洞"**：原先只比棋盘底色深一点点，而棋子之间本来就有 3px 的缝，
    两者同色，根本分不出"这一格是空的"和"这只是两块之间的缝"——而华容道全靠这个判断。
    现在底色压深到 #2e251c + 强内阴影，和棋盘底色的 RGB 差值 148。
  - **空格的 DOM 顺序必须在棋子之前**：同层元素靠后的画在上面，反过来加的话
    20 个深色空格会把棋子整个盖住（踩过，整盘变黑只剩文字）。
    这个坑很隐蔽——空格是 pointer-events:none，**点击照样能用**，光靠"能不能操作"发现不了，
    得直接盯 DOM 顺序。单测有一条专门验这个。
  - **出口画成「底墙上的缺口」，不要画成 2×2 的虚线框。** 一开始画了个 2×2 的金色虚线框，
    两个毛病：① 它标的是"曹操要占的位置"，不是出口本身；② 压在棋子上，曹操一挪过去
    就被自己挡没了（试过拆成"底层门洞 + 顶层永远可见的框"，能看见但仍然别扭）。
    华容道本来的画法就是**底墙上留个缺口**——缺口在棋盘外面，永远不会被棋子挡住。
    棋盘高度 = 5 格 + 底墙，缺口开在底墙的第 2~3 列。
  - **2048（js/games/g2048/）**：五个文件。核心的 move() 要返回详细位移信息
    （slides / merges），否则渲染层做不了滑动和合并动画——2048 没有动画就没有手感。
    动画分两拍：先平移（CSS transition），过渡结束后整块重建 + 弹一下。
    第二拍敢整块重建，是因为第一拍结束时牌已经在目标位置了，重建看不出跳变。
  - **提示写「建议」不写「最优」**：2048 每步都有随机成分，不存在必胜走法。
    用期望最大化（玩家取最大、随机按 0.9/0.1 加权取平均），深度 3 平均 1ms，
    自对弈能稳定过 1024。估值权重：空位数 > 单调性 > 平滑度。
  - 坑：合并的两块里**本来就在目标位置**的那块不会出现在 slides 里（没动就不报），
    写测试断言时要注意，那里只有 1 条位移而不是 2 条。
  - **浏览器测试里能用同步就别用 await setTimeout**：「五款游戏都能进能出」原先每款
    await 两次定时器，在无头浏览器里被节流拉到几十秒一次，五次就超时中断了——
    而打点显示其实早就走完了。enter()/leave() 本来就是同步改视图的，根本不需要等。
  - **数字华容道（js/games/slide/）**：六个文件，core / solver / hints / view / store / app。
    平台层一行没改就接上了——这就是当初把 registry 抽出来的意义，加游戏的成本只有游戏本身。
  - 打乱用「从终局倒着走」而不是随机排列：随机排列一半无解（逆序数奇偶性），
    倒着走必然有解，步数还顺便当了难度旋钮。
  - **提示分两档是刻意的**：3×3 的 A* 精确给最优解；4×4/5×5 状态空间是 1e13 / 1e25，
    实时搜不完，退成「就近一步」并在弹窗里写明不保证最短。拿贪心冒充最优解比不给提示更糟。
  - 两个被单测抓出来的坑：贪心回退原先在没有正收益时返回 -1（滑块经常要先把块挪开让路），
    提示直接变 null、界面上表现成「点了没反应」；hints.best 原先只看 state === 'won'，
    而 create() 出来的终局 state 还是 ready，会给已完成的盘面凭空算出一条提示。
  - 布局坑：fit() 不能量父元素——盘面的宽高就是父元素撑开的，循环依赖，首次渲染量到 0，
    盘面缩成 102px。也别量 .board-area（同样被内容撑大，切档位尺寸会飘），直接按视口算。
  - **启发式那一档踩过大坑：提示来回打转**（"把 10 往上滑"→照做→"把 10 往下滑"，无限循环）。
    根因：一歩贪心卡在局部最优时所有走法都是负收益，并列又取了第一个候选。
    最终解法两条，分工不能混：
      · **「不许撤销上一歩」必须是硬约束** —— 周期 2 一定表现为同一块牌来回挪，掐掉回退就没了。
        注意 avoid 要记**上一歩发出时空格的位置**，不是被挪的牌的下标（走完就失效了）。
      · **禁忌表（空格最近去过的位置）只能当软约束** —— 做成硬约束的话邻居一被禁光就没得选，
        只能放开限制，防打转形同虚设（实测漏过周期 2）。
    另外 lookahead 要「取往后 k 步能达到最低总距离的第一步」，不是「找第一条能改善的序列」——
    后者玩家只走第一步就重新规划，计划的收益全丢（实测 600 步只降 8 格）。
  - A* 要加距离闸：远未接近完成时它必然失败，却要把节点上限跑满（5×5 白等 60ms）。
- 分层：`js/platform/`（游戏无关）→ `js/core/`（9×9 数独族共用算法与渲染原语）→ `js/games/<游戏>/`。
- **加一款新游戏** = 写一个文件调 `SD.Registry.register({...})` + index.html 加一行 `<script>`，
  平台层一行都不用改。契约字段见 `js/platform/01-registry.js` 的注释。
- 对局页骨架由游戏自己用 `SD.Shell.topbar()` 搭，壳不预设任何控件（扫雷的盘面和 9×9 不是一回事）。
- 数据分命名空间：数独仍是 `sudoku-studio:v1`（**一个字节都没动**），全局是
  `puzzle-hub:global:v1`（主题 + 通关点数）。主题放全局是有意的——它是显示偏好，不是游戏进度；
  但严格说这是除点数外第二项共享的东西，改动前想清楚。
- 遮罩只有一个 `#shell-overlay`（fixed 铺满整屏）。原先每个视图各一个，
  出题途中切视图会收错节点、灰幕留在屏幕上点不掉。
- 出题是异步的，两处令牌：`session`（离开游戏作废）和 `preparing`（玩家明确开局后作废后台备局）。
  少任何一个都会出现「晚一步落地的结果把玩家刚选的题顶掉」。
- **扫雷（js/games/mines/）和数独族不共用任何逻辑**，只复用平台层。
  它有自己的 core / solver / hints / view / store / learn / app 七个文件。
  - 求解器 02-solver.js 只读 open/flag/num/mines，**绝不读 b.mine**（那是答案）。
    tests/mines-test.js 有一条断言专门把 b.mine 抹掉再跑一遍，结论必须一模一样。
  - 枚举用「逐格计数」而不是位掩码：位掩码卡在 32 位，而边界分量动辄四五十格，
    一超限就整块放弃枚举，L4/L5 会几乎永远用不上。
  - **全局雷数约束不能参与连通分量划分**——它覆盖所有未知格，会把整片边界串成一个
    巨型分量、次次超限。全局雷数由卷积那一步管。这个坑曾让枚举失败率高达 91%。
  - 稀有技巧（单格已够数、全局雷数）在随机对局里几乎不出现，教程示例用手工夹具
    （M.fixtures），单测和教程共用同一份，别两处各画一遍。
- **纯消除型提示是个隐形坑**：提示列表按**盘面**算，而「删除候选」不改盘面，
  所以同一条解法会永远排在第一——玩家点完「执行」面板一个字不变，像卡死。
  另外没开笔记时 notes 全是 0，消除删了个寂寞，盘面也纹丝不动。
  现在：applyStep 先把受影响格子的当前候选填进 notes 再删（看得见），
  hintList 过滤掉「结论已经在笔记上」的纯消除型解法（面板会往前走）。
  注意判据要求**所有**受影响格子都有笔记，否则刚开局会把消除型解法一次滤光。
- **踩雷后要摊开全部雷**：core 里的 revealMines 曾被定义、导出，但**没有任何地方调用**；
  视图里那行 `open && b.mine[i] && lost` 的前置也不成立（雷根本没被翻开），
  结果一颗雷都没摊出来，结算文案却写着「雷也全部摊开了」。
  现在按 XP 行为：摊开所有**没插旗**的雷，插对的旗保持原样，插错的旗标红。
- **测试名不能比断言大**：这条用例名叫「摊出全部雷并标出错旗」，却只数了爆炸点和错旗，
  雷摊没摊开压根没验——所以这个 bug 一直溜过去。名字承诺什么就得断言什么。
- **扫雷视觉**：未扫格必须是凸起的按钮（灰色面 + 左上 2px 高光 / 右下 2px 阴影），
  已扫格压平留白。只靠底色深浅区分（surface-2 vs surface）实测根本看不出来。
  配色用 color-mix 从主题变量组合，7 套主题自动成立。
- **改 CSS 别用 JS 的 .replace() 批量替换**：没命中时它静默返回原文，不报错。
  曾因此把扫雷的 --mine-* 变量「写进去」了却压根没落地，白排查一轮。用 edit 工具，锚点不对会直接失败。
- **杀手数独（js/games/killer/）和数独共用 js/core**：棋盘、对局控制器、技巧引擎、棋盘渲染都复用。
  - 对局控制器已经提到 `js/core/11-game.js`（SD.GameBase），六个依赖由各游戏注入：
    settings / recordTechnique / conflicts / isComplete / hints / solve。数独那边是薄包装。
  - 棋盘渲染加了 `opts.cages`（笼子虚线 + 笼和标签）和 `highlightCage`（选中即点亮整个笼子）。
  - **依赖唯一解/致命模式的技巧在杀手盘面上不成立**：交换两格会破坏笼和，「第二个解」不存在。
    唯一矩形整族被排除。这条是性质测试跑出来的（它删掉了真解数字），不是推测。
  - 枚举用的组合表 COMBOS[k][s] 在加载时一次算完（512 个子集）。
  - 出题是「先出终盘再切笼子」，切完验唯一解，不唯一就重切。笼子越大越难唯一：
    2 格笼 83%、5 格笼 20%、6 格笼 0%，所以上限卡在 4 格。
  - **标准族里 finny-fish / 强制链那几条在杀手盘面上极贵**（开局全空，搜索空间拉满，
    实测 finny-fish 一次 28ms）。它们被标成 expensive，只有别的技巧都推不动时才跑——
    提示面板从 67ms 降到 1ms。
  - 踩过的坑：`B.UNITS[u]` 是 Int8Array，`filter`/`slice` 返回的还是 Int8Array，
    而 `Int8Array.prototype.map` 会把字符串强转成 0——讲解里的坐标全渲染成「0、0」。
    现在单测里有一条断言盯着「step.cells 必须是真数组」。
  - **切笼子的种子不能按固定随机顺序挑**：轮到靠后的格子时四邻早被分完，长不出第二格，
    直接变成单格笼。实测中等档平均每局 15.7 个单格笼，整盘碎成一片。改成优先挑
    「还有未分配邻居」的格子当种子（roomy），再加一道 absorb 收尾合并漏网的，降到 0.3 个。
  - 入门档**故意**关掉 roomy：单格笼等于白送一个数字，是唯一能让入门题保持简单的手段
    （笼子一收干净就得上 45 法则）。所以单格笼不是 bug，是分档设计。
  - **45 法则算外格时不能要求数字互不相同**：内格同属一个单元必然不同，外格跨笼子可以重复。
    第一版拿组合表去过外格，过约束，删掉了真解。现在内格用组合表、外格用「允许重复」判定。
  - **cage-trial 不能参与评级**：它强到一用就通关，算进去的话所有题都落到 L5，等级失去分辨力。
    rate() 固定用 maxLevel 4 量，needsTrial 单独作为最高一档。
  - 求解器有 NODE_LIMIT（12 万节点）：笼子开大后个别盘面搜索会爆炸（实测最长 2800 万节点），
    一个病态盘面就能把页面冻死。被截断时 hasUnique 一律判「没验出唯一解」，换个切法重来。
    上限从 40 万降到 12 万是因为单次求解最坏要两秒，25 次尝试就是几十秒。
  - 出题有三道闸：每轮 15 次尝试、整轮 4 秒硬上限（**内外层都要查**，只查外层等于没查）、
    切不出唯一解就逐级收窄笼子尺寸重来（收到 2 格笼时唯一解率 85%，几乎必成）。
  - 出题循环里「至少拿到一道唯一解的题再谈时间预算」：反过来的话预算到点时手上空空，
    只能抛「出题失败」——那比多等一两秒糟得多。
  - **视觉**：带笼子渲染时不画「相邻宫交替淡底」（它看起来就像分组，和笼子边框抢注意力）；
    笼子虚线 2px / 52%，**并且内缩 2px 画在格子里面**——贴着格子边画会和九宫格粗线糊成一条。
    **别想着「每条笼边只画一次」去省平行线**：那样线会归到邻居笼子名下，本笼子看起来就缺了下、右两面。
    每格四面该画的都画，宁可边界处多一条平行虚线。
  - **教程演示局面是离线预生成的静态数据**：`tests/build-killer-demos.js` → `js/games/killer/08-demos.js`。
    它们跟玩家、跟时间无关，不该每个玩家各算一遍；展开教程从 48 秒降到 7 秒。
    数据里存了**候选数状态**——演示局面是「一路推到某一步」的中间态，光有盘面复现不出来
    （cage-trial 就依赖前面累积的消除）。出题逻辑改了要重跑生成脚本，单测会验数据是否过期。
  - 踩过的坑：脚本按数字前缀加载，`04-generator` 依赖 `03-techniques`。
    顺序写反时 Node 测试（手动列文件）能过、浏览器里却 `Cannot read properties of undefined`。
